Acceptance closure diagnostics
==============================

These tools are for a dedicated disposable VM, not the production periodic
collector and not a substitute for an untraced performance acceptance batch.
The original idle/periodic throughput and P99 bounds and window-throughput
bound remain unchanged. No positive P1 receipt is generated by this pilot.

Reproducible pilot
------------------

``closure_probe_vm.py`` runs OFF, IDLE, IP and owner with two container
workloads, one target and one bystander. It uses the verified ARM64 Image,
2-second windows and 2000 scheduled requests/second. A second, reversed-order
diagnostic control sets only the test process's timer slack to 1 ns. Default
timer slack and all original acceptance workload parameters are unchanged.
Each cell is one diagnostic observation, not a five-pair confidence interval.

The workload exports its existing due/begin/finish timestamps after the
measurement window. A task-scoped sched_waking/sched_switch trace uses the
guest monotonic clock, fixed per-CPU buffers and bounded export. PID identity,
trace clock, overruns and truncation accompany the data. The trace and resource
sampler themselves cost CPU and memory; their results cannot approve overhead.

``latency_schedule.py`` associates up to 32 largest requests with a unique
observed waking event and subsequent switch-in. Absent or ambiguous matches
stay unknown. Text timestamps have finite precision. Due-to-waking includes
timer coalescing/delivery and possibly previous-request backlog; it is not a
host scheduler attribution. Waking-to-running is a scheduling interval, not
proof of a lock holder or cross-container causality. Guest tracing alone does
not establish why a host vCPU was delayed.

Resource boundary
-----------------

Each trial creates a fresh observer cgroup before the daemon starts. Worker
descendants inherit it. The management sampler and container workloads are in
separate cgroups. Memory charge high-water marks, memory categories/events and
CPU counters are retained from before start through daemon exit and a fixed
five-second observation tail. The guest-wide snapshots include unrelated
diagnostic/workload work and are not labeled observer background CPU.

``resource_timeline.py`` distinguishes kernel-maintained memory.peak from a
sampled RSS peak. It rejects resets, incomplete reads and missing tail evidence.
It does not add worker CPU to an ancestor cpu.stat total, add overlapping
memory.stat categories, or turn a zero task-cgroup tail into zero kernel work.
Retained charged file pages after exit may include intentionally retained logs;
they are not automatically a leak. Work later than the fixed tail is unknown.

The fixed OLK source makes the missing boundaries concrete:

* kernel/bpf/syscall.c: bpf_map_kmalloc_node and related wrappers use the map's
  saved memcg plus __GFP_ACCOUNT. This supports charging those allocations to
  the creator, including uses outside the creating task. It does not establish
  coverage of every BPF/JIT/verifier allocation.
* arch/arm64/net/bpf_jit_comp.c uses bpf_jit_binary_alloc. In kernel/bpf/core.c,
  that rounds code plus header/padding, charges bpf_jit_current and calls
  bpf_jit_alloc_exec/module_alloc. The global JIT counter is not the observer's
  cgroup memory.peak. Executable pages and associated metadata require a
  separate, version/configuration-specific bound.
* With CONFIG_PERF_USE_VMALLOC=y, kernel/events/ring_buffer.c:rb_alloc uses
  vmalloc_user plus a GFP_KERNEL descriptor. rb_free schedules rb_free_work.
  Neither mapped process RSS nor observer cpu.stat proves that all allocation
  metadata and deferred work are accounted to the observer.
* kernel/events/core.c allocates perf_event from a SLAB_PANIC cache with
  GFP_KERNEL, and allocates contexts separately. Event count, ring pages and
  metadata must be audited independently, not hidden in a map fdinfo number.
* kernel/bpf/core.c:bpf_prog_free schedules bpf_prog_free_deferred on a shared
  workqueue. Owner identity and task CPU are not automatically inherited by
  that worker. A finite tail can observe activity but cannot prove attribution
  or a hard completion-time bound by itself.

No general allocator, perf or memcg algorithm is changed by these diagnostics.
The 64-MiB total and asynchronous CPU acceptance checks remain incomplete until
these paths have accountable evidence. A small charged peak is insufficient.

Raw runtime readers
-------------------

``runtime_evidence.py`` verifies source-bound session records, explicit fault
events, cancellation results and cleanup evidence. It reports bounded
subclaims separately: sampled sessions, three cancellation stages, eight
injected resource boundaries and the full declared FD-limit sweep. Missing
cases remain BLOCKED. These subsets cannot approve allocator internals,
crash recovery, storage failures at every stage or combined CPU enforcement.
